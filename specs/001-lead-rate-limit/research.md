# Исследование (Research): Ограничение частоты заявок

## 1. Где хранить счёт

- **Решение**: в таблице заявок. У заявки появляется отпечаток адреса подключения; счёт — число заявок с тем же
  отпечатком за последние 10 минут.
- **Почему**: заявки уже сохраняются в базу, общую для всех копий сайта (FR-009); после перезапуска данные на месте;
  в счёт сами собой попадают только сохранённые заявки (FR-003). Нового сервиса не нужно.
- **Отвергнуто**:
  - счёт в памяти сайта (как у входа в админку) — у каждой копии свой счёт, обнуляется при выкладке;
  - Redis — новый сервис на Render, ради одной проверки слишком дорого;
  - отдельная таблица попыток — дублирует то, что уже есть в заявках.

## 2. Как хранить адрес

- **Решение**: HMAC-SHA256 от адреса с ключом `SECRET_KEY`, первые 32 шестнадцатеричных символа.
- **Почему**: FR-010 — по отпечатку видно «тот же адрес», но адрес не восстановить. Простой хеш без ключа не годится:
  адресов IPv4 всего ~4 млрд, их перебирают за минуты. С ключом без него перебор невозможен.
- **Следствие**: `SECRET_KEY` должен быть одинаковым у всех копий. Если ключ не задан, `config.py` при каждом запуске
  генерирует случайный — у каждой копии свой, отпечатки одного адреса расходятся, и порог умножается на число копий.
  Поэтому на хостинге (задана переменная `PORT`) сайт без `SECRET_KEY` не запускается: `main.py` останавливается
  с понятной ошибкой. Локально ключ по-прежнему необязателен.
- **Отвергнуто**: хранить адрес как есть — персональные данные (152-ФЗ) без нужды.

## 3. Чьё время

- **Решение**: окно считается по часам базы: `created_at > now() - interval '10 minutes'`.
- **Почему**: `created_at` ставит база (`server_default=now()`); часы разных копий сайта могут расходиться.

## 4. Две заявки одновременно

- **Решение**: проверка и сохранение — в одной транзакции под блокировкой по отпечатку
  (`pg_advisory_xact_lock`). Вторая параллельная заявка с того же адреса ждёт первую и видит её в счёте.
- **Почему**: без блокировки бот, отправивший 20 заявок разом, пройдёт проверку всеми — SC-001 нарушен.
  Блокировка по отпечатку не мешает заявкам с других адресов (FR-004).
- **Отвергнуто**: уникальные ограничения в таблице — для «не больше N за окно» не подходят.

## 5. Адрес подключения

- **Решение**: `request.client.host`. На хостинге uvicorn запущен с `proxy_headers=True`, поэтому там настоящий адрес
  покупателя из `X-Forwarded-For`, а не адрес балансировщика. Неизвестный адрес — строка `"unknown"`, общий счёт.
- **Хостинг**: Render — только на время разработки; рабочий сайт будет в российском дата-центре (Yandex Cloud или
  Selectel). Решение от хостинга не зависит: база общая, адрес — из заголовка балансировщика. Но сейчас сайт доверяет
  `X-Forwarded-For` от кого угодно (`forwarded_allow_ips="*"`). На Render это безопасно: до сайта доходит только прокси
  Render. На новом хостинге сайт должен быть доступен только через балансировщик (или доверять заголовку только от
  него) — иначе бот подставит любой адрес и обойдёт порог. Это задача переезда, не этой фичи (план фич).
- Функция `client_ip(request)` уже есть во входе в админку (`app/admin/auth.py`, `_client_ip`). По принципу V она
  переезжает в ядро (`app/core/http.py`), вход в админку берёт её оттуда.

## 6. Ответ на заявку сверх порога

- **Решение**: код 429, та же форма с ошибкой (карточка товара) или страница корзины с ошибкой (корзина).
- **Почему**: обработчик формы на карточке (`calc.js`) заменяет форму ответом при любом коде — правка JavaScript
  не нужна; без JavaScript обычная отправка формы тоже показывает страницу с сообщением.
- Текст: «Слишком много заявок. Попробуйте через несколько минут или позвоните: <телефон из настроек>».

## 7. Порог в настройках

- **Решение**: `LEAD_LIMIT=5`, `LEAD_LIMIT_MINUTES=10` в `app/core/config.py` с этими значениями по умолчанию.
- **Почему**: поменять порог без выкладки кода, если офисные покупатели начнут упираться.
