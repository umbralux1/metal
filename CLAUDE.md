# Правила работы агента

**Принципы и технические правила проекта — в конституции `.specify/memory/constitution.md`** (архитектура, чистое
ядро, тесты, модели чтения, адреса и SEO, безопасность, миграции, статика). Прочитать её перед любой работой
с кодом. Здесь — только как работать. Правило живёт в одном месте: в конституции или здесь, не в обоих.

## Как работать
- **Не додумывать.** Неясно или задачу можно понять по-разному — спросить до кода. Предположения называть явно.
  Есть путь проще — сказать.
- **Точечные изменения.** Каждая изменённая строка следует из задачи. Соседний код, комментарии и форматирование
  не «улучшать», стиль — как в файле.
- **Своё убирать, чужое записывать.** Ставшее ненужным из-за своих изменений — удалить в том же коммите.
  Замеченный по пути долг — в `docs/tech-debt.md`, исправлять отдельным коммитом.
- **Рефакторинг — отдельным коммитом `refactor:`**, только там, где задача прямо затрагивает код.
- **План с проверками**: у задачи из нескольких шагов (и без спецификации) — шаги и как проверить каждый.
- **Язык**: имена в коде — по-английски; интерфейс, комментарии, документация и спецификации — по-русски;
  сообщения коммитов — по-английски, `feat:` / `fix:` / `refactor:` / `docs:` / `chore:`.

## Без явной просьбы не делать
- Коммиты (их делает владелец; агент — только когда попросили), `git push`, `make deploy`, любые действия на Render.
- `make db-reset`, `DROP`/`TRUNCATE`, удаление и правка уже применённых миграций.
- Правку `.env` и `deploy/render.env`; удаление файлов, кроме своих временных.

## Общие функции — искать здесь, прежде чем писать свою
- Числа: `format_decimal` (11.700 → «11,7», в шаблонах — фильтр `num`), `parse_decimal` («11,7», «1 000» → Decimal) —
  `app/core/numbers.py`. Новое поле с числом — в `NUMBER_FIELDS` в `tests/test_numbers.py`.
- Деньги: `format_rub` (₽ на сайте) — `app/core/templating.py`; `rub_to_kop`, `kop_to_rub` (поля админки) —
  `app/admin/money.py`.
- Время: `format_local_time`, `site_year` — в часовом поясе сайта, `app/core/templating.py`.
- Телефон: `normalize_phone` (`app/leads/phone.py`); ИНН: `is_valid_inn` (`app/leads/inn.py`).
- Поиск и адреса: `normalize_search`, `slugify`, `fix_layout` — `app/catalog/utils.py`; адрес страницы каталога —
  `.url` у моделей, `paths.url(path)`.

## Порядок работы над фичей (Spec Kit)
Спецификация — источник правды: любое изменение поведения начинается с правки спецификации. Фича — папка
`specs/NNN-имя/` и ветка с тем же именем. Команды `/speckit-*` лежат в `.claude/skills/`; если они недоступны как
слэш-команды (агент работает удалённо), прочитать `SKILL.md` команды и выполнить её шаги.

1. **Имя и ветка.** Агент предлагает имя `NNN-краткое-имя` (номер — следующий после последней папки в `specs/`),
   владелец создаёт ветку: `git switch -c NNN-краткое-имя`. Спецификация создаётся с этим же именем
   (`--short-name`, `--number`).
2. **Спецификация** — `/speckit-specify`: что и зачем, сценарии «дано / когда / тогда», требования `FR-###`,
   критерии `SC-###`, что не делаем. Неясности — `/speckit-clarify`. **Стоп: владелец согласует спецификацию.**
3. **План** — `/speckit-plan`: таблицы, модули, контракты; «Constitution Check» по воротам конституции,
   отступления — с обоснованием. При желании — `/speckit-checklist`.
4. **Задачи** — `/speckit-tasks`, затем `/speckit-analyze` (спецификация, план и задачи не противоречат друг другу).
5. **Красные тесты** — первая фаза задач: тест на каждое `FR-###`, в описании `NNN:FR-###`.
   **Стоп: владелец прогоняет — новые падают, старые проходят** (охранные — на уже существующее поведение —
   зелёные сразу, агент их называет).
6. **Реализация** — `/speckit-implement`, остальные фазы задач; `make check`, снимки, скриншоты (конституция,
   «Ворота качества»). Статус спецификации — «Реализовано».
7. **Сдача** — агент перечисляет файлы и даёт готовые `git add …` и `git commit -m "feat: … (NNN)"`; коммит
   и слияние ветки в `main` делает владелец.

Без спецификации: правка только вёрстки или текста (проверка скриншотами), рефакторинг, ошибка (раздел «Ошибки»).
Описания фич живут в `specs/`; старые `docs/<фича>.md` переезжают туда, когда у части сайта появляется спецификация.

Статус в плане фич (Claude Doc «План фич», https://claude.ai/artifact/ChucedRNpdXLgXfXRCfrCN): «в работе» после
спецификации, «готово» после коммита; у фичи — ссылка на `specs/NNN-имя/`. Новые задачи, долг и решения
из разговора — туда же. Нет доступа к документу — написать статус в ответе.

## Ошибки
Журнал — `docs/bugs.md`, у каждой ошибки номер `BUG-NNN`. База регрессов: тест на каждую исправленную ошибку.
1. **Запись.** Найденная ошибка (владельцем, проверкой, по пути) — сразу в `docs/bugs.md`: что видно, как
   воспроизвести (браузер, ширина окна, адрес, шаги), статус «открыта». В плане фич — строка с номером и статусом.
2. **Сверка со спецификацией.** У части сайта есть спецификация — указать в записи: требования нет (дописать
   `FR-###` в спецификацию) или код его не выполняет.
3. **Регрессионный тест** воспроизводит ошибку, в описании — номер: `"""BUG-001: …"""` (и `NNN:FR-###`, если есть).
   Владелец прогоняет: тест падает. Ошибка видна только в браузере — тест в браузере.
4. **Исправление** — после этого, коммит `fix: … (BUG-NNN)`. В записи — причина, коммит, имя теста,
   статус «исправлена».

Не воспроизводится у агента — сначала выяснить, где и как воспроизводится (браузер, данные), а не исправлять наугад.

## Проверки перед сдачей
- `make check` (= ruff + mypy + import-linter + pytest). `make audit` — уязвимости в зависимостях (нужен интернет),
  перед выкладкой.
- Рефакторинг, обновление зависимостей, правка общего кода (`base.html`, калькулятор, генератор адресов, сохранение
  в админке) — снимки: `make snapshot` до изменений, `make snapshot-diff` после (`scripts/snapshot.py`). Рефакторинг —
  «отличий нет»; фича — отличаются только задуманные ответы. Итог `snapshot-diff` — в сдаче работы. Вёрстку снимки
  не ловят (сравнивается HTML) — для неё скриншоты на 1280 и 360 px.
- Новые частые команды — целью в `Makefile` с описанием после `##` (оно попадает в `make help`).
