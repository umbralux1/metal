# Правила проекта

## Как работать
- **Не додумывать.** Неясно или задачу можно понять по-разному — спросить до кода. Предположения называть явно.
  Есть путь проще — сказать.
- **Минимум кода.** Только то, что просили. Без абстракций под один случай, без настроек и обработки ошибок
  «на всякий случай». Можно вдвое короче — переписать.
- **Точечные изменения.** Каждая изменённая строка следует из задачи. Соседний код, комментарии и форматирование
  не «улучшать», стиль — как в файле.
- **Своё убирать, чужое записывать.** Ставшее ненужным из-за своих изменений — удалить в том же коммите.
  Замеченный по пути долг — в `docs/tech-debt.md`, исправлять отдельным коммитом.
- **Рефакторинг — отдельным коммитом `refactor:`**, только там, где задача прямо затрагивает код.
- **План с проверками**: у задачи из нескольких шагов — шаги и как проверить каждый.
- **Язык**: имена в коде — по-английски; интерфейс, комментарии и документация — по-русски; сообщения коммитов —
  по-английски, `feat:` / `fix:` / `refactor:` / `docs:` / `chore:`.

## Без явной просьбы не делать
- Коммиты (их делает владелец; агент — только когда попросили), `git push`, `make deploy`, любые действия на Render.
- `make db-reset`, `DROP`/`TRUNCATE`, удаление и правка уже применённых миграций.
- Правку `.env` и `deploy/render.env`; удаление файлов, кроме своих временных.

## Статика (CSS, JS, картинки)
- В шаблонах — только `{{ static_url('css/main.css') }}`: отпечаток `?v=…`, чтобы браузер не брал старый файл
  из кэша. Прямые `/static/...` запрещены, кроме шрифтов (проверяет `tests/test_deploy.py`).

## Адреса каталога
- Адреса товаров ведёт генератор `app/catalog/landings.py`: товар с размером лежит внутри посадочной
  (`…/40x40/40x40x2/`). Любая смена адреса — через генератор или `app/catalog/paths.py`, с 301 со старого.
- Раздел товара определяется по `category_id`, не по началу адреса.

## Миграции и запуск на Render
- Миграции запускает `app/core/startup.py` до старта сервера. Ожидание блокировок ограничено (`migrations/env.py`),
  при неудаче — повторы и понятная ошибка. Новые миграции проверять на базе с открытой транзакцией по таблице.
- Служебные команды в `migrations/env.py` коммитить до `context.configure`, иначе Alembic не зафиксирует миграцию.
- Миграция с данными выдерживает мусор в рабочей базе (`CASE` с проверкой формата перед приведением типа, как в
  `0005`) и проверяется тестом: вверх, вниз, снова вверх. Упавшая миграция не даст сайту запуститься на Render.

## Архитектура
- **Модуль = предметная область**: `app/catalog`, `app/cart`, `app/leads`, `app/delivery`, `app/seo`. Публичное
  у модуля — `service.py` и модули с типами и чистыми функциями (у доставки `cargo`, `pricing`, `selection`).
  `models.py` — только самому модулю, админке, миграциям и тестам; для `app/delivery` проверяет import-linter.
- **Зависимости в одну сторону, без циклов**: `core` ← `seo` ← `catalog` ← `leads` ← `cart` ← страницы и админка.
  `seo` — только общее (мета-теги, разметка организации и крошек); SEO страниц каталога — в `app/catalog/seo.py`.
  `delivery` не знает про корзину и товары: получает простые данные (`CargoSpec`) и возвращает простые данные
  (`VehicleQuote`). Проверяет import-linter — контракты в `pyproject.toml`.
- **Сначала данные, потом код.** Фича начинается с таблицы и типов (dataclass, Pydantic), затем функции над ними.
  Мало продуманных структур и много маленьких функций; одно понятие — одна структура, без почти одинаковых копий.
- **Чистое ядро, грязная оболочка.** Расчёты (цены, подбор машин, пересчёт единиц) — чистые функции: без базы, сети,
  текущего времени и случайности, тестируются без базы. Чтение и запись базы, HTTP, логи — в оболочке, она зовёт ядро.
- **CQS**: функция либо читает и возвращает данные без побочных эффектов, либо меняет состояние и возвращает минимум
  (id, результат). По имени видно, что она делает: `list_…`, `get_…` — чтение; `create_…`, `update_…` — изменение.
- **Модели чтения**: запросы для страниц возвращают готовые структуры (dataclass), а не ORM-объекты.
  Шаблоны не обращаются к связям моделей и не вызывают запросов к базе.
- **Без N+1.** У связей `lazy="raise"`, загружать явно в запросе (`selectinload`, `joinedload`). Число запросов
  проверяет `tests/test_query_counts.py` — новую страницу со списком товаров добавить туда.
- **Pydantic — на границах** (формы, параметры запроса, настройки, ответы внешних API): данные проверяются один раз
  на входе. Внутри — `@dataclass(frozen=True)`.
- **Структура растёт по необходимости.** Маленький модуль — `models.py` + `service.py`. Расчётная логика, которую
  стоит тестировать без базы, — отдельный файл (`app/delivery/pricing.py`); файл больше ~400 строк — разбить по смыслу.
  Пустых файлов «на вырост» не заводить.

## Код
- Имя говорит, что функция делает: глагол + предмет (`quote_delivery`, не `calc`). Единицы в именах:
  `_kop`, `_kg`, `_m`, `_km`. Цель — по сигнатуре понять функцию, не читая тело.
- Полные аннотации типов у публичных функций; на границах модулей — dataclass, не голые `dict`.
- Docstring в одну строку, если название и типы не объясняют всего (единицы, особые случаи).
- Перед новым кодом искать готовое; одну логику не писать дважды. Мёртвый код — см. «Как работать».
- Функция длиннее ~50 строк — повод разбить. Новая зависимость в `pyproject.toml` — с объяснением в коммите.
- Тесты проверяют поведение через публичные функции, а не внутренности. Исключение — проверки базы, миграций
  и сида: им можно напрямую к моделям и таблицам.

## Безопасность
- **SQL** — только через ORM или параметры запроса, без f-строк (ловит ruff `S`).
- **XSS**: `|safe` — только из списка `SAFE_ALLOWED` в `tests/test_templates_rules.py`, `Markup` — только для своего
  HTML (ruff `S704`). Данные покупателей и из админки — никогда без очистки.
- **CSRF**: формы, которые что-то меняют (заказ, заявка), — только POST. Сейчас защищает `SameSite=Lax` у cookie
  корзины; появятся личные кабинеты — нужны CSRF-токены.
- **Редиректы** — только на свои относительные адреса (`/…`), не на внешний URL из параметра
  (`tests/test_security.py`).
- **Секреты** — только в переменных окружения: не в коде, не в логах, не в ответах с ошибками.
  Исключение — тестовые данные в `deploy/render.env`.
- **Входные данные** проверяются Pydantic на границе: длины, диапазоны, форматы (телефон, ИНН, километры).
- **Перебор и спам**: ограничение частоты на формы заявок и вход в админку.
- **Персональные данные** покупателей (имя, телефон, ИНН) не писать в логи.
- Уже существующие нарушения (частота заявок не ограничена, телефоны пишутся в лог) — в `docs/tech-debt.md`;
  новый код — по правилам, старое исправлять отдельной задачей.

## SEO
Поиск — главный источник заказов, SEO-ошибки тихие. `tests/test_seo_pages.py` проверяет страницу каждого типа:
один `h1`, title, description, canonical, sitemap, `noindex` у служебных, разметку schema.org.
Новый тип публичной страницы — добавить в `INDEXABLE` (с нужной разметкой) или `NOINDEX`.

Тестом не проверяется:
- Адреса: латиница, нижний регистр, слэш в конце. Смена адреса — только с 301 со старого.
- Цены, описание, наличие отдаются в HTML с сервера, не через JS. Данные разметки — из того же источника,
  что и текст на странице.
- Картинки ниже первого экрана — `loading="lazy"` (`width` и `height` проверяет `tests/test_templates_rules.py`).
  Без блокирующих скриптов в `<head>`; новая тяжёлая библиотека на фронте — с обоснованием.
- Всё работает на ширине 360 px без горизонтальной прокрутки.

## Порядок работы над фичей (TDD)
Фича — **один коммит**: тесты, реализация и документация вместе. Подзадачи нужны для плана и документации,
не для коммитов.
1. **Тесты.** Агент пишет тесты на новое поведение. Владелец прогоняет: новые падают, старые проходят.
2. **Реализация и документация** — только после этого. `make check` зелёный, изменения проверены на сайте
   (скриншоты на 1280 и 360 px). Описание — в `docs/<фича>.md` (например, `docs/delivery.md`): что делает,
   таблицы и поля, формулы, как менять в админке; краткие сведения о таблицах — в `docs/database.md`.
3. **Коммит** `feat: …` делает владелец, когда проверил, что всё работает. Сдавая работу, агент перечисляет
   файлы коммита и даёт готовые `git add …` и `git commit -m "…"`.

Правка только вёрстки или текста без нового поведения — без новых тестов, проверка скриншотами.
Тесты под реализацию не подгонять: если тест оказался неверным, исправить его и объяснить почему.

Статус в плане фич (Claude Doc «План фич»,
https://claude.ai/artifact/ChucedRNpdXLgXfXRCfrCN): «в работе» после тестов, «готово» после коммита.
Новые задачи, долг и решения из разговора — туда же. Нет доступа к документу — написать статус в ответе.

## Проверки перед сдачей
- `make check` (= ruff + mypy + import-linter + pytest), совместимость с Python 3.11 (Render).
  `make audit` — уязвимости в зависимостях (нужен интернет), перед выкладкой.
- Новые частые команды — целью в `Makefile` с описанием после `##` (оно попадает в `make help`).
