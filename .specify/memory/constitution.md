# Конституция проекта «Дом металла»

Интернет-магазин металлопроката: FastAPI, Jinja2 (страницы рендерит сервер), SQLAlchemy async, PostgreSQL, SQLAdmin,
Python 3.11. Разработка — на Render, рабочий сайт — в российском дата-центре (Yandex Cloud или Selectel): код
к хостингу не привязывается. Конституция — источник принципов и технических правил; порядок работы агента — CLAUDE.md.

## Core Principles

### I. Модули и зависимости в одну сторону

- **Модуль = предметная область**: `app/catalog`, `app/cart`, `app/leads`, `app/delivery`, `app/seo`. Публичное
  у модуля — `service.py` и модули с типами и чистыми функциями (у доставки `cargo`, `pricing`, `selection`).
  У каталога `service.py` нет: публичное — `repository.py`, `read_models.py` и чистые модули.
- `models.py` — только самому модулю, админке, миграциям и тестам; для `app/delivery` и `app/leads` проверяет
  import-linter (заявки создаются только через `create_lead` в `app/leads/service.py`).
- **Зависимости в одну сторону, без циклов**: `core` ← `seo` ← `catalog` ← `leads` ← `cart` ← страницы и админка ←
  сборка приложения (`app/main.py`) и запуск (`app/bootstrap.py`). `core` не знает ни одного модуля: функции
  шаблонов из модулей (иконки, счётчик корзины) регистрирует `app/main.py`.
- `seo` — только общее (мета-теги, разметка организации и крошек); SEO страниц каталога — в `app/catalog/seo.py`.
- `delivery` не знает про корзину и товары: получает простые данные (`CargoSpec`) и возвращает простые данные
  (`VehicleQuote`).
- Проверяет import-linter (контракты в `pyproject.toml`, в `make check`); исключения (`ignore_imports`)
  не добавляются — нарушение исправляется или записывается в `docs/tech-debt.md`.

### II. Сначала данные, чистое ядро

- **Сначала данные, потом код.** Фича начинается с таблицы и типов (dataclass, Pydantic), затем функции над ними.
  Мало продуманных структур и много маленьких функций; одно понятие — одна структура, без почти одинаковых копий.
- **Чистое ядро, грязная оболочка.** Расчёты (цены, подбор машин, пересчёт единиц) — чистые функции: без базы,
  сети, текущего времени и случайности, тестируются без базы. Чтение и запись базы, HTTP, логи — в оболочке,
  она зовёт ядро. Чистые модули перечислены в контракте import-linter «Чистые функции»; новый — добавить туда.
- **CQS**: функция либо читает и возвращает данные без побочных эффектов, либо меняет состояние и возвращает минимум
  (id, результат). По имени видно, что она делает: `list_…`, `get_…` — чтение; `create_…`, `update_…` — изменение.
- **Pydantic — на границах** (формы, параметры запроса, настройки, ответы внешних API): данные проверяются один раз
  на входе. Внутри — `@dataclass(frozen=True)`.
- **Деньги** — целые копейки (`_kop`), без float.

### III. Сначала тесты (не обсуждается)

- Каждое функциональное требование спецификации (`FR-###`) — хотя бы один тест; в описании теста ссылка вида
  `001:FR-003` (номер спецификации и требования). Каждая ошибка (`BUG-NNN`) — регрессионный тест с номером
  в описании. Связь требований с тестами проверяет `tests/test_specs.py`.
- Порядок: тесты написаны → владелец прогоняет и видит, что новые падают, а старые проходят → только потом
  реализация.
- Тест под реализацию не подгоняется: оказался неверным — исправить и объяснить почему. Регрессионный тест
  не удаляется и не ослабляется. Ошибка, видная только в браузере, — тест в браузере (Playwright, WebKit).
- Тесты проверяют поведение через публичные функции, а не внутренности. Исключение — проверки базы, миграций
  и сида: им можно напрямую к моделям и таблицам.

### IV. Страницы без скрытых запросов

- **Модели чтения**: запросы для страниц возвращают готовые структуры (dataclass), а не ORM-объекты. Шаблоны
  не обращаются к связям моделей и не вызывают запросов к базе. Каталог — `app/catalog/read_models.py`;
  проверяет `tests/test_read_models.py` (новую страницу добавить туда).
- **Без N+1.** У связей `lazy="raise"`, загружать явно в запросе (`selectinload`, `joinedload`). Число запросов
  проверяет `tests/test_query_counts.py` — новую страницу со списком товаров добавить туда.

### V. Одно понятие — одно место

- Одна логика не пишется дважды. Перед новой функцией ищется готовая: общее перечислено в CLAUDE.md,
  «Общие функции» (числа, деньги, время, телефон, ИНН, поиск, адреса страниц).
- Расползшееся место после исправления охраняется тестом-правилом: числа — `tests/test_numbers.py`
  (точку на запятую и обратно меняет только `app/core/numbers.py`; новое поле с числом — в `NUMBER_FIELDS`),
  статика — `tests/test_deploy.py`.
- Найденный по пути долг — в `docs/tech-debt.md`, исправляется отдельной задачей.

### VI. Адреса и SEO не ломаются

Поиск — главный источник заказов, SEO-ошибки тихие.
- Адреса товаров ведёт генератор `app/catalog/landings.py`: товар с размером лежит внутри посадочной
  (`…/40x40/40x40x2/`). Любая смена адреса — через генератор или `app/catalog/paths.py`, с 301 со старого.
  Раздел товара определяется по `category_id`, не по началу адреса.
- `tests/test_seo_pages.py` проверяет страницу каждого типа: один `h1`, title, description, canonical, sitemap,
  `noindex` у служебных, разметку schema.org. Новый тип публичной страницы — в `INDEXABLE` (с нужной разметкой)
  или `NOINDEX`.
- Тестом не проверяется, но обязательно:
  - адреса — латиница, нижний регистр, слэш в конце;
  - цены, описание, наличие отдаются в HTML с сервера, не через JS; данные разметки — из того же источника,
    что и текст на странице;
  - картинки ниже первого экрана — `loading="lazy"` (`width` и `height` проверяет `tests/test_templates_rules.py`);
    без блокирующих скриптов в `<head>`; новая тяжёлая библиотека на фронте — с обоснованием;
  - всё работает на ширине 360 px без горизонтальной прокрутки.

### VII. Простота

- Только то, что требует спецификация. Без абстракций под один случай, без настроек и обработки ошибок
  «на всякий случай». Можно вдвое короче — переписать.
- **Структура растёт по необходимости.** Маленький модуль — `models.py` + `service.py`. Расчётная логика, которую
  стоит тестировать без базы, — отдельный файл (`app/delivery/pricing.py`). Функция длиннее ~50 строк, файл
  больше ~400 строк — повод разбить. Пустых файлов «на вырост» не заводить.
- **Код:** имя говорит, что функция делает — глагол + предмет (`quote_delivery`, не `calc`); единицы в именах
  (`_kop`, `_kg`, `_m`, `_km`). Полные аннотации типов у публичных функций; на границах модулей — dataclass,
  не голые `dict`. Docstring в одну строку, если название и типы не объясняют всего.
- Новая зависимость — с объяснением в коммите. Каждое отступление от принципов обосновывается в плане
  (раздел «Отступления от конституции»).

## Технические правила

- **Статика.** В шаблонах — только `{{ static_url('css/main.css') }}`: отпечаток `?v=…`, чтобы браузер не брал
  старый файл из кэша. Прямые `/static/...` запрещены, кроме шрифтов (проверяет `tests/test_deploy.py`).
- **Миграции.** Запускает `app/bootstrap.py` до старта сервера. Ожидание блокировок ограничено
  (`migrations/env.py`), при неудаче — повторы и понятная ошибка. Новые миграции проверять на базе с открытой
  транзакцией по таблице. Служебные команды в `migrations/env.py` коммитить до `context.configure`, иначе Alembic
  не зафиксирует миграцию. Миграция с данными выдерживает мусор в рабочей базе (`CASE` с проверкой формата перед
  приведением типа, как в `0005`) и проверяется тестом: вверх, вниз, снова вверх. Упавшая миграция не даст сайту
  запуститься на хостинге. Применённые миграции не правятся.
- **Несколько копий.** Сайт может работать в нескольких копиях (выкладка, рост нагрузки) и перезапускаться.
  Общее состояние — счётчики, ограничения, блокировки — в базе, не в памяти процесса; в памяти — только то, что
  можно потерять (кэш). Настройки, которые должны совпадать у копий (`SECRET_KEY`), на хостинге обязательны —
  без них сайт не запускается (`main.py`).
- **Совместимость** — Python 3.11.

## Безопасность

- **SQL** — только через ORM или параметры запроса, без f-строк (ловит ruff `S`).
- **XSS**: `|safe` — только из списка `SAFE_ALLOWED` в `tests/test_templates_rules.py`, `Markup` — только для своего
  HTML (ruff `S704`). Данные покупателей и из админки — никогда без очистки.
- **CSRF**: формы, которые что-то меняют (заказ, заявка), — только POST. Сейчас защищает `SameSite=Lax` у cookie
  корзины; появятся личные кабинеты — нужны CSRF-токены.
- **Редиректы** — только на свои относительные адреса (`/…`), не на внешний URL из параметра
  (`tests/test_security.py`).
- **Секреты** — только в переменных окружения: не в коде, не в логах, не в ответах с ошибками.
  Исключение — тестовые данные в `deploy/render.env`.
- **Входные данные** проверяются Pydantic на границе: длины, диапазоны, форматы (телефон, ИНН, километры).
- **Перебор и спам**: ограничение частоты на формы заявок (счёт в базе, `specs/001-lead-rate-limit`) и вход
  в админку.
- **Адрес покупателя** — только через `client_ip` (`app/core/http.py`), хранить — только отпечатком
  (`client_fingerprint`). Заголовку `X-Forwarded-For` сайт доверяет только от своего балансировщика: напрямую,
  мимо него, сайт недоступен.
- **Персональные данные** покупателей (имя, телефон, ИНН, адрес подключения) не писать в логи.
- Уже существующие нарушения — в `docs/tech-debt.md`; новый код — по правилам, старое исправлять отдельной задачей.

## Ворота качества

Каждая фича проходит их по порядку; подробный порядок работы — CLAUDE.md, «Порядок работы над фичей».

1. Своя ветка `NNN-имя`, совпадающая с папкой `specs/NNN-имя/`.
2. Спецификация согласована владельцем до плана; в ней нет `[NEEDS CLARIFICATION]`.
3. План прошёл «Constitution Check»; каждое отступление записано и обосновано.
4. Владелец видел красные тесты до реализации.
5. `make check` зелёный (ruff, mypy, import-linter, pytest). Правка общего кода — снимки
   `make snapshot` / `make snapshot-diff` с объяснимыми отличиями; вёрстка — скриншоты на 1280 и 360 px.
6. Коммит делает владелец; в `main` — только через его слияние.

## Governance

Конституция — источник принципов и технических правил проекта; CLAUDE.md — порядок работы агента и ссылки сюда.
Правило не повторяется в двух местах: при переносе или изменении оно живёт в одном документе, второй ссылается.
При противоречии исправляется неверный документ в том же коммите; до исправления действует конституция.
Изменение конституции — через `/speckit-constitution`, с повышением версии: MAJOR — принцип убран или переопределён,
MINOR — добавлен или существенно расширен, PATCH — уточнения формулировок. Каждый план проверяется на соответствие
в разделе «Constitution Check»; еженедельный обзор кода сверяется с конституцией и спецификациями.
